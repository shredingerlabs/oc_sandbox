oc-sandbox – Quickstart Guide

Der OpenCode Sandbox ist eine fertige Entwicklungsumgebung in einem Container (Podman, rootless) – inklusive OpenCode als KI-Coding-Assistent. Diese Anleitung begleitet dich vom nichts installierten System bis zur ersten produktiven OpenCode-Session. Container-Grundkenntnisse werden nicht vorausgesetzt; nur ein Terminal zu öffnen und cd zu tippen solltest du können.

1. Was ist oc-sandbox?

oc-sandbox stellt dir pro Projekt einen Podman-Container bereit – eine abgeschlossene, gehärtete Linux-Umgebung, in der dein Projektcode liegt und in der OpenCode (Terminal- und Weboberfläche) läuft. Deine Zentrale ist die TUI (Text-Oberfläche im Terminal, basierend auf gum): Sie führt durch Container-Bau, Projekt-Einrichtung und Start.

Der Container gibt es in vier Editionen, je nach Bedarf:

EditionInhaltFür wen?
basePython + Systempaketereine Python-/CLI-Arbeit
webbase + Node/TypeScript/PlaywrightWeb-/TS-Projekte
embeddedbase + ARM-Toolchains/Arduino/MicroPythonMikrocontroller
fullweb + embedded (Standard)alles gemischt

Im Zweifel: full wählen – die Editionen unterscheiden sich nur im Umfang der vorinstallierten Werkzeuge.

2. Installation unter Windows 11 (WSL)

Ohne Linux-Installation geht es über WSL2 mit Ubuntu 24.04. Vier Schritte, einmalig:

2.1 WSL2 + Ubuntu 24.04 installieren

Eine PowerShell als Administrator öffnen und ausführen:

wsl --install -d Ubuntu-24.04

Danach Windows neu starten. Beim ersten Start von Ubuntu wirst du nach Benutzername und Passwort gefragt – dieses Passwort gilt für sudo im Linux-Terminal.

Ubuntu öffnen: Im Windows-Startmenü „Ubuntu 24.04“ suchen – es öffnet sich ein Linux-Terminal. Alle folgenden Befehle gehören dorthin, nie in die PowerShell.

2.2 systemd sicherstellen

Podman braucht systemd. Ubuntu 24.04 bringt es unter WSL normalerweise schon mit. Prüfen:

ps -p 1 -o comm=

Steht dort nicht systemd, es aktivieren:

sudo tee /etc/wsl.conf <<'EOF'
[boot]
systemd=true
EOF

Dann in der PowerShell (nicht in Ubuntu!) den WSL-Dienst neustarten:

wsl --shutdown

Ubuntu wieder öffnen, die Prüfung mit ps -p 1 -o comm= wiederholen.

2.3 Benötigte Pakete installieren

Im Ubuntu-Terminal:

sudo apt-get update
sudo apt-get install -y git curl podman passt fuse-overlayfs jq

Rootless-Podman prüfen – es muss true liefern:

podman info --format '{{.Host.Security.Rootless}}'

2.4 oc-sandbox installieren

Weiter mit Abschnitt 4 – dort läuft der Installations-Befehl identisch in Ubuntu/WSL. Auch der Desktop-Shortcut funktioniert: Bei --shortcut erscheint „OC Sandbox.lnk“ im Windows-Startmenü und startet die TUI direkt.

3. Voraussetzungen (Linux)

Auf Ubuntu 22.04/24.04 bzw. Debian. (Nutzer:innen von WSL haben diesen Schritt bereits in Abschnitt 2.3 erledigt und überspringen direkt zu Abschnitt 4.)

sudo apt-get update
sudo apt-get install -y git curl podman passt fuse-overlayfs jq

Rootless-Podman prüfen – es muss true liefern:

podman info --format '{{.Host.Security.Rootless}}'

4. Installation

Ein einziges Kommando (Ubuntu/Debian/WSL):

curl -sL \
  https://raw.githubusercontent.com/shredingerlabs/oc_sandbox/main/scripts/install.sh \
  | bash -s -- --symlinks --shortcut
Alle drei Zeilen gehören zu einem Befehl – die Backslashes \ am Zeilenende sind Shell-Zeilenfortsetzung. Du kannst alle drei Zeilen zusammen kopieren und einfügen.

Warum bash -s --? Der klassische … | bash-Aufruf ignoriert Argumente. Alles nach -- wird ans Skript durchgereicht. Hier bedeuten die Flags:

FlagWirkung
--symlinksLegt den Befehl oc-sandbox in ~/.local/bin an – damit startest du die TUI jederzeit mit einem Wort.
--shortcutDesktop-Shortcut: Linux → Eintrag „OC Sandbox“ im Anwendungs-Menü; WSL → OC Sandbox.lnk im Windows-Startmenü.
--install_path <pfad>Installationspfad (Standard: ~/.oc-sandbox).
--version <tag>Bestimmte Version statt dem neuesten Release.
--forceBestehende Installation ohne Nachfrage überschreiben.

Das Skript installiert außerdem gum für die TUI (sollte das scheitern, läuft die TUI in einem einfachen Textmodus weiter) und benutzt nie automatisch sudo.

5. First Setup: erster Build, erstes Projekt, erste Session

TUI starten (entweder durch den Menü-Shortcut oder im Terminal):

oc-sandbox

5.1 Container bauen – und jetzt: Geduld

Der erste Container-Build dauert sehr lange (ggf. viele Minuten bis über eine Stunde, je nach Rechner und Internetleitung). Das ist kein Fehler – es werden Toolchains, Browser und Bibliotheken heruntergeladen und kompiliert. Es lohnt sich auch: Späterer Neustart nach einem Systemneustart ist deutlich schneller.

Im Hauptmenü Build Container wählen und die gewünschte Edition bauen (all baut alle). Danach ist der Bau abgeschlossen – nur bei Versions-Updates wiederholen.

5.2 Erstes Projekt anlegen (New Project)

Menüpunkt New Project. Der Wizard fragt Schritt für Schritt:

SchrittWas gefragt wirdEinsteiger-Antwort
1. ProjektnameAnzeigename, z.B. mein-erstes-projektkurzer, klarer Name
2. PfadWohin? Standard: ~/oc-sandbox/<name>Standard lassen, oder eigener Pfad z.B. ~/projects/kunde-x
3. VCS-Hostnone, GitHub, GitLab (öffentlich oder eigenes), eigener Hostkein Git nötig → none; sonst dein Host
4. TokenPersönlicher Zugriffstoken (z.B. GitHub PAT), wird verborgen abgefragtnur bei VCS ≠ none
5. Git-Identitätuser.name, user.emaildein Name/E-Mail, nur bei VCS ≠ none
6. Start-Optionconsole / opencode / webopencode (empfohlen, siehe Tipps)
Was ist ein Token? Ein „persönlicher Zugriffstoken“ (PAT) ist ein langes Passwort, das du in den Einstellungen deines Git-Hosts (GitHub/GitLab) erzeugst und hier einmal einfügst. Es bleibt projekt-lokal gespeichert und wird nie angezeigt.
Erste OpenCode-Session: unbedingt mit /exit beenden. In der ersten Session richtet OpenCode die Skills ein – schließt du sie mit Ctrl+C oder Ctrl+D ab, kann diese Einrichtung unvollständig bleiben. Warte, bis die Session komplett durchgelaufen ist, und tippe dann /exit.

Die Ersteinrichtung (Konfiguration des Knowledge-Graph-Indexers „CBM“, danach die interaktive Skills-Einrichtung über eine OpenCode-Session) läuft danach automatisch. Sollte ein Schritt scheitern, bietet die TUI Retry, Go back oder Exit – ein Retry wiederholt nur den fehlgeschlagenen Teil.

5.3 Erste Session mit OpenCode

Menüpunkt Start last used project oder Open Project. Je nach gewählter Start-Option:

  • opencode – OpenCode-TUI öffnet sich direkt
  • console – interaktive Shell im Container, dort z.B. opencode eintippen
  • web – OpenCode im Browser (nächster Abschnitt)

6. Wie Projektordner und Container zusammenhängen

Es gibt zwei Blickwinkel:

Host-Sicht (dein Linux/WSL-Dateisystem)

Dein Projekt liegt unter ~/oc-sandbox/<projektname>/ (oder dem gewählten Pfad) und enthält Konfigurationsordner, die du im Alltag nicht anfassen brauchst:

~/oc-sandbox/<projektname>/
  project/            ← hier liegt dein eigentlicher Code (inkl. .git!)
  .opencode_config/    ← sandbox_config.json, projektspezifische Einstellungen
  .opencode_data/       ← OpenCode-Daten (Auth, Tokens)
  .ssh_local/           ← SSH-Keys dieses Projekts
  .git_local/           ← Git-Identität + Credentials
  .cbm_cache/           ← Knowledge-Graph-Datenbank

Container-Sicht (aus OpenCode heraus)

Im Container siehst du nur den Ordner ~/oc-sandbox/<projektname>/project – er ist dort nach ~/project gemountet (installiert als /home/dev/project). Von Konfigurationsordnern wie .opencode_config oder .git_local merkt der Container nichts – sie bleiben auf dem Host und werden als interne Verbindungen benutzt.

Für die OpenCode Web-Variante: Auf dem Host ist der oberste Projektordner ~/oc-sandbox/<name>, im Container ist es nur ~/project. Deshalb heißt die Option in der Weboberfläche auch ~/project – und du wählst sie dort in der Liste.

7. Nutzung: starten mit Symlink, Shortcut und TUI

7.1 TUI starten

Am einfachsten mit dem Symlink (via --symlinks installiert):

oc-sandbox

Oder durch den Desktop-/Windows-Startmenü-Shortcut (via --shortcut).
Alternativ direkt über den Installationspfad: ~/.oc-sandbox/scripts/start-tui.sh.

7.2 Hauptmenü

MenüpunktFunktion
Start last used projectZuletzt genutztes Projekt mit gespeicherten Einstellungen starten.
Open ProjectRegistriertes Projekt auswählen und starten.
New ProjectProjekt neu anlegen (Wizard aus Abschnitt 5.2).
Build ContainerContainer-Images bauen (nur einmal nötig).
SettingsConfig-Backup/-Restore, Container stoppen, Deinstallation.
ExitTUI beenden.
Läuft der Container des Projekts schon, wird er wiederverwendet (per podman exec angedockt) statt neu gestartet – das geht deutlich schneller.

7.3 Die Web-Option (OpenCode im Browser)

Hast du als Start-Option web gewählt, läuft im Container dauerhaft ein OpenCode-Webdienst. Die URL zeigt dir die TUI an, typischerweise:

http://127.0.0.1:4096

Port-Suchbereich: Falls 4096 belegt ist, probiert die TUI automatisch die Ports 4096–4196 durch.

Im Browser (OpenCode-Weboberfläche):

  1. Projekt hinzufügen – über die zugehörige Aktion in der Weboberfläche
  2. ~/project auswählen – steht ganz unten in der Ordnerliste (siehe Pfadmodell, Abschnitt 6)
  3. Session starten – los geht's mit OpenCode im Browser

Beim Zugriff auf ein laufendes Projekt fragt die TUI, wie du zugreifen willst: bei web zwischen „Show Web URL“ und „Console (bash)“, bei opencode zwischen „OpenCode (configured)“ und „Console (bash)“. Eine Console-Session ist eine unabhängige Shell und ändert deine konfigurierte Start-Option nicht.

8. Tipps für den Alltag

Tipp 1: Jede Aktion in eine neue Session

OpenCode-Session tragen Kontext (Tokens). Über 100.000–150.000 Token wird das Modell langsamer und teurer und verliert Fokus. Der Trick: pro Aufgabe eine neue Session (z.B. „Bug X fixen“ in einer Session, „Feature Y“ in der nächsten), nicht alles in eine einzige Session stopfen.

Tipp 2: Die TUI verwenden

Bei der Projekteinrichtung Start-Option opencode (oder console + dort opencode) wählen – die TUI zeigt mehr Infos zur laufenden Session als die Weboberfläche und gibt dir über /session einen Überblick über bisherige Sessions.

Tipp 3: Skills nutzen

Skills sind fertige Anleitungs-Werkzeuge für OpenCode – kleine „How-does-it-work“-Bausteine, die das Modell bei passenden Aufgaben automatisch lädt (z.B. einen Test-Workflow oder einen Setup-Assistenten). Aufruf im OpenCode-TUI:

/skills

Das First-Setup installiert automatisch bereits die ersten Skills über den Befehl setup-matt-pocock-skills (Modell opencode/big-pickle) – deshalb ist die erste Session so wichtig (siehe Warnung in 5.2). Danach kannst du über /skills weitere hinzufügen oder aktivieren.

9. Troubleshooting

„Build dauert so lang – stimmt da was nicht?“

Nein, normal (siehe 5.1). Erster Build dauert sehr lange; auch der erste Start nach einem Systemneustart braucht noch Zeit. Wenn der Fortschritt aber komplett stillsteht, TUI beenden, Container prüfen (podman ps -a) und den Build wiederholen.

„Erster Start nach dem Neustart ist langsam“

Beim ersten Start nach einem System- oder WSL-Neustart muss die Podman-Umgebung neu hochfahren – das dauert. Einfach abwarten; ab dem zweiten Projektstart in derselben Sitzung geht es deutlich schneller.

„Die TUI sieht anders aus / hat keine bunten Menüs“

Das Skript konnte gum nicht installieren und die TUI ist in den einfachen Fallback-Textmodus gefallen. Alle Funktionen sind trotzdem da, nur optisch schlichter. Internetverbindung prüfen, dann Installation wiederholen (--force).

„Web-URL nicht erreichbar“

Die URL (z.B. http://127.0.0.1:4096) gilt auf dem Rechner, auf dem der Container läuft. Steht der genaue Port in der TUI-URL-Anzeige. Bei der Web-Option muss im Container ein Git-Repo im project/-Ordner vorliegen – der Wizard legt automatisch eines an, wenn keins existiert.

„Setup ist abgebrochen / fehlgeschlagen“

Das Projekt bleibt registriert. TUI neu öffnen, Open Project wählen und Retry drücken – es wird nur der unvollständige Schritt wiederholt, nicht alles.
