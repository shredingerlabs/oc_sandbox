# Workspace replaces project as the domain noun

The wish-list for the WebUI-first effort renames the central domain noun, and a pre-rename noun spread across user-facing words, data files, and on-disk layout for years: the registered unit users create, import, and configure was a **project**. We rename it to **workspace** everywhere users can see — menu words and help text, `projects.json` → `workspaces.json` (top key `workspaces`), config keys (`default_workspace_path`, `workspace_source`, `workspace_kind`, values unchanged), script artifacts (`init-workspace.sh`, `configure-project.sh` → `configure-workspace.sh`, `--workspace_kind`), the content directory `project/` → `workspace/`, and the container mount `/home/dev/project` → `/home/dev/workspace` — and, since the Go files change anyway, internal Go identifiers/packages (e.g. `internal/openworkspace`, `registry.Workspace`, script vars `WORKSPACE_ROOT`) rename too. A one-time migration converts existing roots and data files; mechanics live with the migration/compatibility plan.

**Depth boundary**: every user-visible word and every file/identifier a user can see or type moves; `oc-sandbox` naming (the tool itself), the `.opencode_config/`-family infra directories, and historical ADRs/specs stay. Script output becomes English, trimmed to the needed minimum (specific errors, `--help`, one final success line — no tutorial echoes; docs own guidance).

**Banned synonyms** for the noun, glossary style: *project* (pre-rename name), *project folder*, *project root* (now workspace root), *app*, *instance*, *sandbox* (that is the whole tool), *container* (a workspace is not its container), *repo* (a repo is the git source/folder inside a workspace; not every workspace contains code or a repo). Legitimate survivors of the word "project": the PKM vault's own knowledge-management sense, `create-release.sh`'s `PROJECT_ROOT` (the release repo's root), repo-metadata references to "the oc-sandbox project", open-source credits, and the archival record.

**Considered options**: dual-name legacy support (`project/` `workspace/` both accepted forever) rejected — one canonical name keeps every layout-checking script single-branch; footgun-free German ("Arbeitsbereich") rejected for the loanword *Workspace* in the German-facing docs, with script echo output switched to minimal English instead; keeping internal Go identifiers as `project` rejected — renaming rides the same PRs the string changes demand, and mismatched symbols would erode the new vocabulary.

**Consequences**: workspaces shipped before the rename keep working only through the one-time migration (registry filename + top key + field/key renames with registry version bump to `2.0`, in-root content-directory rename, mount-path change); the Workspace terminology mapping ticket records the full term table; referenced-but-unrelated uses (CBM session wiring `codebase-memory-mcp (project=home-dev-workspace)` included) follow the same mapping.

Decided 2026-11-09 via [Grilling: Workspace terminology mapping](https://github.com/shredingerlabs/oc_sandbox/issues/134).
