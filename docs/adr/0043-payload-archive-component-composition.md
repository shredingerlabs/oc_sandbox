# Payload-Archive Component Composition with a Tagged-Component Cache

Each toolchain builds once per machine as a **component image** (`opencode-sandbox-tc-<id>:<hash12>`); a workspace's **set image** (`opencode-sandbox-set:<hash12>`) is assembled from its members' **payload archives**: the generated component Dockerfile wraps the recipe fragment and ends with an injected dump step (payload = dpkg `-L` of newly installed packages ∪ pip RECORD paths ∪ recipe-declared `# extra:` paths ∪ the whole `/home/dev`; PM state = the dpkg status file + `/var/lib/dpkg/info` entries), and the generated set Dockerfile COPYs each member's archive, then one RUN extracts in canonical order, merges PM state as a dpkg stanza-union (info entries unioned; a contested package's last canonical writer wins files and stanza alike), re-emits fragment ENVs (alphabetical-last on duplicate keys), runs `ldconfig`, removes the staging area — pure Dockerfile/buildah primitives, always `--network=none`. Identity is content-addressed: the first 12 hex of the hash over sorted (toolchain id, recipe content hash) pairs + the base recipe content hash (component hashes include the base recipe hash, so a base bump re-addresses everything). The measurable target holds: adding an already-built toolchain costs one incremental assembly (5.0–5.5 s measured at the real 1.66 GB base); a never-built toolchain costs one component build (73–179 s), reused by every workspace thereafter.

## Considered Options

- **Generated prefix-chain Dockerfile** (devcontainer-Features-shaped, validated prior art): meets only warm rebuilds — add-one re-runs every later layer (~23 s canonical, 11 s incremental with per-parent-set-only reuse). Rejected on measurement.
- **Naive `COPY --from` filesystem merge**: measurably corrupts dpkg status (163→127 stanzas, gcc unknown) and carries a full base per component (+84 % set size); whole-rootfs merging re-breaks the seconds target at real scale (20–60 s, (1+N)×base on disk).
- **fs-merge with package-state regeneration** (the apko/rpm-ostree model) or Nix-style store composition: a whole new composition mechanism with new failure modes, for no measured benefit over the stanza union. Rejected.

## Consequences

- **Incremental delta assembly is an optimization, never a second semantics.** It runs iff a valid parent exists — a set image whose members (by component hash) form a strict subset of the new set's, same base/component versions — AND the contest check passes: new members' dpkg/pip names ∩ the parent union's = ∅, read host-side from image labels (`tc.pkgs` on components, the merged union label on sets) via `podman image inspect`, never a container start. Everything else is full canonical assembly — fresh sets, member drops, base bumps/recipe changes, deleted or pre-label parents, any contest. Alphabetical-last-wins stays the sole contested resolution; multi-add applies new members alphabetically (≡ canonical among the new). A sanity-gate failure on an incremental assembly auto-falls-back to full canonical with one honest log line — that fallback is the repair path. Identity is content alone; an optional non-normative provenance label (mode + parent tag) serves diagnostics only.
- **The layer cache is never the cache.** "Cached" = tagged component images exist for every member; assembly checks member tags, builds missing, assembles. A user-run `podman image prune` deletes the whole cross-build layer cache — the design treats prunes as cache-clearing events; tags survive routine prunes, and residual `system prune -a` losses cost rebuilds, never correctness.
- **Host floor: podman ≥ 4.0** (`RUN --mount=type=cache` in component builds; effectively the Ubuntu 24.04 pocket / Debian 12). Below the floor, builds refuse with an update hint — no silent slow path.
- Budget formula: set ≈ base + Σ member payloads; component ≈ base + 2× payload. Sets are self-contained after assembly — components are never runtime-pinned.
- `COPY --from=<image>` composes files only (ENV/ENTRYPOINT/LABELS never flow), so fragment ENVs are re-emitted in the set Dockerfile and the footer is uniform `USER dev` + `ENTRYPOINT ["/bin/bash","-l"]`.
- Sanity gates are hard requirements — dpkg `--audit` clean; `dpkg -l` keeps the base's and every member's packages; pip RECORD metadata intact; binaries run — parameterized in `tests/verify-set-image.sh`, a standing acceptance check, never a build flag.
- Networking: component and base builds keep `--network host` (status quo); every assembly invocation passes `--network=none`, so "fully-cached = offline-capable" holds by construction. Builds never traverse squid — no allowlist entries are ever needed for builds.
