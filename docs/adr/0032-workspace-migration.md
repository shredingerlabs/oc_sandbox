# One-time first-start workspace migration (blocking, staged, backup-first, abort-on-error)

The rename (ADR-0030) changes the on-disk register and layout of every pre-rename install: `projects.json` → `workspaces.json` (top key `projects` → `workspaces`), `default_project_path` → `default_workspace_path`, `project_source`/`project_kind` → `workspace_source`/`workspace_kind`, content dir `project/` → `workspace/`. The old binary never read configuration guardedly — the new binary detects and converts a pre-rename install itself, so no migration tool exists outside the release binary.

**Decided shape**: the migration runs **one-time at first start of the new binary, blocking before anything reads config** — between home resolution and `app.Compose` in `cmd/oc-sandbox/main.go`, unlike the silent-init precedent (ADR-0006's update check is non-blocking on purpose; migration must own the surface until it finishes). Guard: `workspaces.json` absent + `projects.json` present → migrate; neither → fresh create (new-name files directly, no migration screen); any of the three general config files still below `2.0` → rerun. **Backup first**: `global_config.json`, the registry file, and every registered root's `sandbox_config.json` pass through the existing `backups/` rotation (ADR-0009; `IsGeneralConfigFile` gains `workspaces.json` + `catalogs.json`) before any stage runs. Then **ordered idempotent stages**: (1) per root, one `os.Rename` of the content dir `project/` → `workspace/`; (2) per root, `sandbox_config.json` key rewrite; (3) registry file rename + top-key rewrite with path fields untouched; (4) `global_config.json` default-path key; (5) one-time token-free seeding of `catalogs.json` per ADR-0031's rules; (6) `version: "2.0"` in all three general config files **written last** — its presence is the migration-complete marker. The migration **aborts on the first error** with a plain error screen and **no auto-restore**: the backups and the idempotent rerun are the recovery path ("fix the cause and restart"). Every stage checks its starting state, so a rerun resumes where it stopped.

**Invariants** (spec §13 constraints on V1 shapes): the migration never repoints registry `path` at the content dir, never re-derives container identities (`container_id` = sha256-12 of the root stays the identity), never renames user-chosen roots, never pre-creates per-repo nesting, and bends nothing beyond the `project/` → `workspace/` mount swap. **Runtime safety**: containers run through — a bind mount survives a host-side directory rename (same inode), and the in-container `/home/dev/workspace` path (`start.sh`'s mount) is consistent for every container started after the rename; images rebuild lazily (ADR-0024 precedent). **Import**: legacy `project/`-layout folders are non-matching for workspace import and get an informational prompt with an explicit **"Convert to workspace layout"** action that runs the same per-root converter (stages 1–2) — never silent. **Update interplay**: `install.sh` removes the stale old-name scripts (`init-project.sh`, `configure-project.sh`); the update installs the new tree only, and the first start afterwards migrates. Post-migration **no legacy read path stays installed**: layout checks accept only `workspace/`, and `start.sh`'s git-init heal keys on the renamed content dir so no legacy `/project/` git-init can resurrect.
