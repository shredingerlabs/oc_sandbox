# Restart always available (WebUI)

ADR-0033 gated the workspace card's Restart behind started-config evidence — active only for a running container whose config fingerprint or image ID drifted — and explicitly rejected "restart-always-available" as a pointless session-killing bounce. A week of use overturned that: the gate made the button sit disabled ("config is current — no restart needed") exactly when users wanted a manual lever anyway (a wedged agent session, a fresh-container do-over), and the evidence machinery (registry keys, staleness helpers, card-side title plumbing) existed solely to power that refusal. **Decided**: Restart is always accessible on every card (ADR-0033's verified stop → fresh-start chain unchanged); the server is the single gatekeeper — a stopped container, busy op key, or pending first-run setup session answers the confirm with a sidecar refusal (a pending setup session also disables the button with the refusal title, mirroring the access buttons), and the edition-image preflight (#117) stays. The staleness machinery is deleted outright: `workspaceStale`/`configFingerprint`/`recordStartedEvidence`, the registry's `started_config_hash`/`started_image_id` keys, and the card's `RestartTitle`/`cardDisabled`. The confirm row restacks: the question on its own line, Confirm/Cancel underneath.

**Consequences**: a restart on an unchanged config is now a deliberate user choice, not a prevented one — the confirm gate carries the session-kill warning alone. A restart recreates the workspace's pod, so it also re-mounts the current workspace allowlist; ADR-0034's Rebuild stays the lighter path (its note referenced the now-deleted fingerprint — Rebuild remains the no-container-bounce route). Old `workspaces.json` files keep their two unread evidence keys; the registry preserves unknown fields, no migration.

Decided 2026-11-17 via Grilling (R1Q1–R1Q5, R2Q6; shared understanding confirmed against the final task list).
