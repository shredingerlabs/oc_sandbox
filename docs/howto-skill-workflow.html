Matt Pococks Skills im Entwickler-Workflow

1. Installation (oc-sandbox: bereits enthalten)

npx skills@latest add mattpocock/skills
npx skills update

oder manuell downloaden: github.com/mattpocock/skills

2. Setup (oc-sandbox: bereits beim container init)

Einmalig pro Repo vom CodingAgent /setup-matt-pocock-skills ausführen lassen. Konfiguriert Issue-Tracker, Triage-Labels, Doku-Ablage.

3. Allgemeine Tipps & Erfahrungswerte

Für jede neue Aufgabe jeweils eine neue Session starten. Bereits nach relativ wenigen Token verlassen die Modelle die „SmartZone“. Dabei „verdummen“ diese langsam und halluzinieren immer stärker. Bei Frontier-Modellen mit 1 Mio. Kontext startet das ungefähr bei 150k Token, bei kleineren entsprechend früher. Das Kompaktieren des Tokenfensters (wenn Kontext voll) führt ebenfalls zu Informationsverlusten und unvorhersehbaren Verhalten.

  • Eine Session pro Anliegen
  • Ergebnisse, wichtige Infos, usw. extern speichern und verfügbar machen (GitHub/GitLab issues oder .md files sind gut geeignet)
  • Compaction besser vermeiden Rangfolge bei voll werdendem Kontext: weiterarbeiten, solange SmartZone übrig → per /handoff Zusammenfassung an weitere Session übergeben (Auch sinnvoll mit /teach wenn etwas unklar ist)
  • Englische Prompts funktionieren meist besser
  • Große Prompts kann man in .md Files auslagern, sauber strukturieren und im Prompt darauf referenzieren
  • Für Planungsaufgaben (wayfinder, grilling, …) und hartnäckige Bugs möglichst gute Modelle und hohes Reasoning einstellen (/variants)
  • Für Implementierungsaufgaben gehen meist auch einfachere Modelle und niedriges oder kein Reasoning
  • Alle unten genannten Skills im Build-Mode ausführen (Umschalten über Tab)
  • Plan-Mode nur für marginale Änderungen.
Phasengrenzen überbrücken: Am Ende einer Phase kann /handoff die Session kompakt für die nächste übergeben — besser als Kontext einfach volllaufen lassen.
Frage unbekannt / Entscheidung nicht möglich ohne Zusatzinfos: Mit /handoff Session-Zusammenfassung übergeben und Sachverhalt mit /teach in neuer Session erklären lassen.

4. Skill-Reihenfolge

SzenarioSkills (Reihenfolge)
Viele Unklarheit bei neuem Projekt oder großen Änderungen — Klärung braucht mehr als eine Session (> 100–150k Token) /wayfinder auf Idee anwenden →
/wayfinder auf jedes wayfinder:xy gelabelte Ticket anwenden →
/to-spec auf fertige wayfinder map →
/to-tickets auf spec →
/implement auf jedes ready-for-agent Ticket
Wenig Unklarheit bei kleinerer oder gut definierter Projektidee oder kleineren Änderungen — Klärung passt in eine Session (< 100–150k Token) /grill-with-docs auf Konzept anwenden → /to-spec am Ende der Session anwenden → /to-tickets auf Spec anwenden → /implement auf jedes Ticket anwenden
Klar definierte, kleine Änderungen — Klärung und Umsetzung passiert in eine Session (< 100–150k Token) /grill-with-docs → /implement
Ganze Spec umsetzen — viele Tickets, die in einer Session orchestriert zusammenpassen (Integration-Branch statt Session pro Ticket) /implement-spec auf die Spec anwenden
Pflege der Codebase (regelmäßig, alle paar Tage; auch vor größeren Builds) /improve-codebase-architecture — bei großen/pre-KI-Repos als Audit
→ gibt Optimierungsvorschläge für KI-optimierte Code-Struktur
Kleines Skript/Programm oder Klärung ohne Codebase ggf. /grill-me → /implement
Hartnäckiger Bug /diagnosing-bugs mit Fehlerbeschreibung ausführen
Incoming Issues von außen (Bug-Reports, externe PRs) /triage — kategorisieren, verifizieren, ggf. grillen, als ready-for-agent-Brief aufbereiten

Unsicher welcher Skill passt? /ask-matt fragen — Router über den ganzen Flow.

Hinweis: /implement lädt am Ende automatisch /code-review nach — deshalb taucht es in den Ketten oben nicht explizit auf. /implement schließt das Ticket nicht selbst: Kriterien prüfen und Ticket selbst abschließen (Commits macht /implement selbst, auf dem aktuellen Branch). Eine Session pro Ticket; unabhängige Tickets können auch parallel laufen.

5. wayfinder vs. grill-with-docs vs. grill-me

Alle sind Grilling-Sessions (Interview zur Klärung). Der Unterschied liegt darin, ob die Klärung dokumentiert wird und ob sie in eine Agenten-Session (= ein Kontextfenster < 100–150k Token) Platz hat.

/grill-me — Alles, auch ohne Codebase (sogar ohne Working-Directory)

  • Interview läuft direkt, keine Dokumentation der Ergebnisse
  • Ergebnis direkt nutzbar für /to-spec oder /implement
  • Gibt es ein Repo (auch für eine kleine Änderung), ist /grill-with-docs die erste Wahl

/grill-with-docs — Codebase, Aufgabe passt in eine Session

  • Interview läuft direkt, aktualisiert CONTEXT.md/ADRs inline
  • Ergebnis direkt nutzbar für /to-spec oder bei kleinen Änderungen /implement

/wayfinder — Codebase, Aufgabe zu groß für eine Session (Kontext würde volllaufen, bevor Klarheit da ist)

  • Baut eine Map zur Klärung: ein Tracker-Issue (wayfinder:map), darunter Child-Tickets — jedes Ticket ist eine Entscheidung (wayfinder:grilling), ein Prototyp (wayfinder:prototype), eine Recherche (wayfinder:research) oder eine manuelle Aufgabe (wayfinder:task, die eine Entscheidung freischaltet — laut Doku der Typ, der am häufigsten übersehen wird), keine Bau-Slice
  • Tickets werden nacheinander, in separaten Sessions, mit dem /wayfinder Skill abgearbeitet („resolve“) bis die Map vollständig ist („Route ist klar“)
  • Fallen laut Doku: keinen Production-Code in der Map schreiben; die Map klein halten — „prototypemaxxing not planmaxxing“; eine Map-Session nach der anderen (nicht parallel)
  • Danach: Map → /to-spec (kollabiert die verlinkten Entscheidungen zu einem baubaren Plan) → /to-tickets → /implement pro Ticket oder /implement-spec auf den gesamten Spec (vgl. §6).
  • Braucht Tracker-Anbindung aus /setup-matt-pocock-skills (GitHub, GitLab, Linear, Jira, Azure DevOps u. a. über „Other“; lokales Tracking über .md-Files ist eine first-class-Option, kein Fallback)

6. implement vs. implement-spec

Beide setzen Tickets um — der Unterschied ist die Orchestrierung:

SkillAblaufWann einsetzen
/implement Ein Ticket pro Session. Implementiert das Ticket direkt im aktuellen Kontext (keine Subagents), committet auf dem aktuellen Branch, lädt am Ende /code-review nach. Schließt das Ticket nicht selbst. Standard für Einzeltickets; ist bereits Pflicht in der /to-tickets-Kette aus §4 — unabhängige Tickets können parallel via separate Sessions laufen.
/implement-spec Ganzer Spec in einer Session. Liest Spec + Tickets als Task-Graph (nicht als Liste), legt eine Integration-Branch an, startet pro Ticket einen Implementer-Subagent in einem eigenen Worktree (auf eigenem Branch) und merged die einzelnen Branches per Merger-Subagent in den Integration-Branch. Wenn das „Frontier“ (nicht blockierte Tickets) wächst, startet der Skill automatisch weitere Subagents für maximale Parallelität. Am Ende /code-review auf dem Integration-Branch. Wenn der Spec aus vielen Tickets besteht, die zusammenpassen und besser in einer Session mit parallelen Subagents fließen, als sie über Session-pro-Ticket abzuarbeiten.

Voraussetzungen

  • Spec + Tickets müssen existieren (aus /to-spec → /to-tickets).
  • Issue-Tracker muss eingerichtet sein (/setup-matt-pocock-skills).
Kontrast zur /implement-Konvention: /implement-spec schließt die Tickets selbst („resolve each ticket the way the issue tracker closes work“) — im Gegensatz zu /implement, wo das manuell passiert. Bei GitHub via PRs auf einem Integration-Branch macht das der Skill automatisch; sonst je nach Tracker.
Setzt voraus, dass die Codebase mit git worktree + separaten Branches umgehen kann; Konflikte zwischen den parallelen Implementer-Branches müssen ggf. beim Merger-Step gelöst werden.

7. Prompt Beispiele

Repo auf GitHub über gh CLI, geht ident. mit glab auf GitLab.

Issue-Nummern sind in der Repo ersichtlich.

Bei lokalem Tracking über .md Files den Namen des Files angeben, statt issues. Lokales Tracking ermöglicht keine Blocking-Abhängigkeiten.

TIPP: Mit einem Leerzeichen vor /skillname wird der Skill über das Skill-Tool geöffnet und nicht komplett im Terminal ausgegeben.

Wayfinder

Starten einer Wayfinder Session:

 /wayfinder Hier die Idee beschreiben. Lose Idee oder umfangreiche, detailierte Anwendungsbeschreibung möglich.

Einzelne Wayfinder Tickets abarbeiten (Skill lädt weitere nötige Skills selbst):

 /wayfinder gh issue #2.

Wayfinder Map in Spec wandeln:

 /to-spec on wayfinder map gh issue #1.

Wayfinder Spec in Tickets wandeln:

 /to-tickets on wayfinder spec gh issue #42.

Umsetzen eines ready-for-agent Ticket zur Implementierung:

 /implement gh issue #3

/implement schließt das Ticket nicht selbst — Kriterien prüfen und Ticket selbst schließen (Commits macht /implement selbst, auf dem aktuellen Branch). Am Ende lädt der Agent aus /implement automatisch /code-review nach.

Implement-Spec

Ganzen Spec (mit allen zugehörigen Tickets) in einer Session umsetzen:

 /implement-spec gh issue #42.

(Nummer der Spec-Issue anpassen — die Tickets sind über Blocking-Links verknüpft.) /implement-spec schließt die Tickets selbst — anders als /implement. Alternativ geht statt /implement-pro-Ticket auch /implement-spec im grill-with-docs-Flow nach /to-tickets. Am Ende läuft /code-review automatisch auf dem Integration-Branch.

Grill-With-Docs

Starten einer grill-with-docs Session:

/grill-with-docs Hier die Idee beschreiben. Lose Idee oder umfangreiche, detailierte Anwendungsbeschreibung möglich.
  1. Am Ende der Session (wenn Ergebnis mehr als eine Implementierungs-Session benötigt): 
    /to-spec
    dann: 
    /to-tickets gh issue #4.
    (Nummer des Tickets anpassen)
    dann Umsetzen eines ready-for-agent Tickets zur Implementierung: 
     /implement gh issue #3.
    (siehe Hinweis oben: Ticket schließt du selbst, /code-review lädt automatisch nach)
  2. Am Ende einer kurzen Session mit wenigen Änderungen: 
     /implement
