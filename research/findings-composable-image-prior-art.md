# Research: prior art for composable toolchain images

Ticket: [#178](https://github.com/shredingerlabs/oc_sandbox/issues/178) · Map: [#176](https://github.com/shredingerlabs/oc_sandbox/issues/176)
Branch: `research/composable-image-prior-art` (never merged; this file is the deliverable)

Question: what prior art exists for **base image + independently versioned, composable install units with strong caching**, and what does it teach oc-sandbox's move from fat edition stages (`dist/Dockerfile`: web, embedded, swdev, matlab, ros2, writing, latex — each `FROM opencode-sandbox-base`, every build busted via `CACHEBUST=$(date +%s)`) to per-workspace toolchain sets?

The measurable target from the map: *adding an already-built toolchain costs seconds; a never-built toolchain costs exactly one build per machine, reused by every workspace thereafter.* Two candidate composition strategies:

- **(a)** generated per-set Dockerfile with one global canonical toolchain order (podman layer cache shares prefix chains only);
- **(b)** built-once tagged component images, filesystem-merged into set images (strict sharing; package-manager state merging is the risk).

Everything below is cited to primary sources (specs, official docs, reference-implementation source code).

---

## Executive summary

1. **devcontainer Features is the closest prior art and a working proof of strategy (a)** — and it runs on Podman, not just Docker. A feature = a self-contained install unit (`devcontainer-feature.json` + `install.sh`), executed as root during image build, **one layer per feature in a deterministic, machine-independent order**. The reference CLI literally does what our strategy (a) proposes: it *generates a Dockerfile* (`Dockerfile.extended`) from the composed set and lets the ordinary layer cache do the sharing ([spec](https://containers.dev/implementors/features/), [CLI source](https://github.com/devcontainers/cli/blob/main/src/spec-node/containerFeatures.ts)).
2. **The canonical order is the load-bearing trick.** The devcontainer spec defines a full deterministic ordering algorithm (dependency graph → round-based sort with a lexicographic "Round Stable Sort" comparator), so *the same set yields the same layer chain on every machine* — which is exactly what makes prefix-chain cache sharing work between workspaces. Order is influenced by recipe-declared dependencies (`dependsOn`, `installsAfter`), not a hand-maintained global list ([spec §Installation order](https://containers.dev/implementors/features/#installation-order)).
3. **Every pattern that merges filesystems safely owns the package database.** Nix (no package DB; store paths + collision-checked `buildEnv`), apko (fresh, fully declarative apk rootfs per build), rpm-ostree (one RPM DB per `/usr` root, regenerated per compose) — none of them *textually merges* dpkg/rpm state from prebuilt images. Raw fs-merge tooling (umoci, buildah) leaves collision and state semantics entirely to the compositor. Naive `COPY --from=<component>` stacking is last-writer-wins and silently corrupts `/var/lib/dpkg/status`, pip site-packages, npm `-g` trees.
4. **Reproducibility is a caching requirement, not a nicety.** Nix: "Using a non-constant date will cause built layers to have a different hash each time, preventing deduplication" ([nixpkgs manual, `streamLayeredImage.mtime`](https://nixos.org/manual/nixpkgs/unstable/#ssec-pkgs-dockerTools-streamLayeredImage)). apko: "Run apko twice and you will get exactly the same binary." Our `CACHEBUST=$(date +%s)` is the exact opposite — the map's decision to kill it is what the record recommends.
5. **Version pinning + an explicit refresh path is the standard replacement for cache busting.** devcontainer lockfiles (`.devcontainer-lock.json`, generated by default, with `devcontainer outdated` / `devcontainer upgrade` as the explicit refresh commands) pin feature versions *and* sha256 integrity digests ([CLI README](https://github.com/devcontainers/cli)). Docker's own best-practices call version pinning "cache busting" done right ([docs](https://docs.docker.com/build/building/best-practices/)).
6. **Earthly shows the hybrid between (a) and (b)**: a *named target* is a stable cache entity (built once, content-keyed, reusable by any set that references it), while sets still compose as sequential layer chains. Cache identity at component granularity, composition at set granularity ([Earthly Earthfile reference](https://github.com/earthly/earthly/blob/main/docs/earthfile/earthfile.md)).
7. **Cache mounts solve the "first build of a toolchain is slow" problem orthogonally** — a persistent apt/pip/npm download cache survives layer rebuilds across all workspaces (`RUN --mount=type=cache`, apt needing `sharing=locked`) ([Docker docs](https://docs.docker.com/build/cache/optimize/), [Earthly docs](https://github.com/earthly/earthly/blob/main/docs/caching/caching-in-earthfiles.md)).

## 1. devcontainer Features (containers.dev spec + devcontainers/cli)

**Model.** A Feature is "self-contained, shareable units of installation code and development container configuration" — `devcontainer-feature.json` (id, semver `version`, `options`, `containerEnv`, `mounts`, lifecycle hooks) plus an `install.sh` entrypoint ([spec](https://containers.dev/implementors/features/)). Referenced per-project in `devcontainer.json`'s `features` object; distributed as OCI artifacts (`ghcr.io/devcontainers/features/go:1`), tgz URLs, or local dirs. `install.sh` "should be executed as `root` during a container image build."

**Execution model (reference CLI).** The CLI generates `Dockerfile.extended` per folder: `FROM $_DEV_CONTAINERS_BASE_IMAGE AS dev_containers_target_stage`, then for each feature a layer that copies the feature into `/usr/local/devcontainer-features/<consecutiveId>` (namespaced discipline) and runs its install script; v2 features additionally `rm -rf` the staged feature dir inside the same layer, and emit their `containerEnv` as Dockerfile `ENV` lines positioned *before their own layer* (positional ENV composition, deterministic because the order is canonical) ([containerFeatures.ts](https://github.com/devcontainers/cli/blob/main/src/spec-node/containerFeatures.ts), [containerFeaturesConfiguration.ts](https://github.com/devcontainers/cli/blob/main/src/spec-configuration/containerFeaturesConfiguration.ts)). Spec: "**Each Feature script executes as its own layer to aid in caching and rebuilding.**" BuildKit `--build-context` supplies feature content; without BuildKit a throwaway content image is built; Podman is a supported variant (with SELinux `label=disable` handling) — i.e., **the generated-Dockerfile model works on podman as-is**.

**Ordering (the canonicalization trick).** "By default, Features are installed on top of a base image in an order determined as optimal by the implementing tool", constrained by: `dependsOn` (hard deps, recursive, options-aware), `installsAfter` (soft deps, only among already-queued features), and user `overrideFeatureInstallOrder`. Ties resolved by the **Round Stable Sort**: lexicographic by fully-qualified ID → oldest-to-newest tag → most user-defined options → sorted option keys → sorted values → digest. Result: the same feature set produces the same installation order everywhere, hence the same layer chain, hence cross-project prefix sharing for free.

**Versioning & idempotency.** Semver per feature; `:latest` implicit, explicit tags/digests to pin; **Feature equality = same manifest digest + same options** — content-addressed identity. Lockfiles pin versions + integrity ("Lockfiles (`.devcontainer-lock.json`) are generated by default when running `build` or `up` to pin feature versions for reproducible builds"; `--frozen-lockfile` to enforce). `devcontainer outdated` / `devcontainer upgrade` = the explicit refresh path. Features run once per image build as cached layers — idempotency is achieved by *not re-running* them, not by making scripts idempotent.

**Merge semantics (config, not filesystem).** Image/run-level composition is specified explicitly: "`privileged`, `init` are included if just 1 feature requires them. `capAdd`, `securityOpt` are concatenated. `containerEnv` is added before the feature is executed as `ENV` commands." Filesystem composition is *sequential inside one build* — dpkg/pip/npm state evolves coherently; there is never a merge of two prebuilt filesystems.

**Meets the target?** Yes, on one machine, under the same conditions our strategy (a) has: identical sets → full cache hit (image export only, seconds); a set extending another set's chain → only the new tail builds; a set that diverges mid-chain → suffix rebuilds (podman/BuildKit layer-cache semantics, [Docker build cache](https://docs.docker.com/build/cache/): "Once a layer changes, then all downstream layers need to be rebuilt as well"). Cross-machine cache transfer exists (`--cache-from`/`--cache-to`, `BUILDKIT_INLINE_CACHE=1` in the CLI) but is out of our scope per the map.

**Pitfalls it documents.** Features may be distro-restricted ("some Features may be authored to work with a certain Linux distro"); user-visible footguns around /usr/local collisions are *not* solved by the spec — sequential execution merely makes them deterministic rather than absent. Renames/deprecations have a defined migration path: `legacyIds` + version continuation, and deprecated features can be folded into a successor's *options* (e.g. `gradle` → `java` with `installGradle: true`) — a good precedent for our edition → bundle → set migration.

**Worth stealing:** deterministic round-stable sort as the global canonical order; `dependsOn`/`installsAfter` in recipes instead of a hand-maintained order list; one layer per toolchain; namespaced staging paths (`/usr/local/devcontainer-features/<id>_<pos>`, `consecutiveId = ${id}_${idx}`); per-machine lockfile with digests + `outdated`/`upgrade` as the explicit refresh UX; positional ENV emission; fold-deprecated-toolchains-into-successor-options migration.

## 2. Nix: dockerTools + buildEnv (deterministic builds, "Nix-in-Docker")

**Model.** Images built *without Docker* from Nix store closures: `buildImage` (single layer; "Only new dependencies that are not already in the existing layers will be copied"), `buildLayeredImage`/`streamLayeredImage` ("multiple layers to improve sharing between images", "one layer per object in the Nix store… the most 'popular' objects in their own layers", `maxLayers` default 100) ([nixpkgs manual §pkgs.dockerTools](https://nixos.org/manual/nixpkgs/unstable/#sec-pkgs-dockerTools)). Composition = union of store paths; a final `symlinkJoin` layer links the requested paths into the image root. `enableFakechroot` is the sanctioned escape hatch for imperative install scripts ("equivalent of `RUN …` in a `Dockerfile`").

**Meets the target?** Better than the target, by construction: store paths are content-addressed and shared across *all* images on the machine (and via binary caches across machines) with **no prefix-chain constraint whatsoever** — composition is order-independent. This is the only family examined where "built once, reused everywhere" holds with zero ordering discipline.

**Merge pitfalls — solved by construction.** No dpkg/rpm DB exists to merge; packages are isolated store paths. Composition collisions are *detected, not silently overwritten*: `buildEnv` "checks for content collisions across the paths by default"; `checkCollisionContents` (default true) fails only when colliding paths differ in content or mode; `ignoreCollisions` (default false) is the explicit escape; the manual warns that overlapping same-priority paths make "the result profile layout potentially affected by the order of elements of `paths`" ([manual §buildEnv](https://nixos.org/manual/nixpkgs/unstable/#sec-pkgs-dockerTools)). ENV composition is a plain `config` attrset — one owner, no positional last-writer-wins.

**The reproducibility law.** `created`/`mtime` default to epoch; "Using a non-constant date will cause built layers to have a different hash each time, **preventing deduplication**." Caching and determinism are the same problem.

**Cost for us.** The whole tool would have to move to a Nix store layout (`/nix/store`, profile symlinks) — a different universe from our apt/Ubuntu recipes and ADR-0019 world. Steal the *invariants* (content-addressed identity, collision-checked unions, static timestamps, per-package layering with a popularity heuristic), not the machinery.

## 3. Earthly (named targets as cache entities)

**Model.** Earthfiles are target graphs; `FROM +another-target` uses another target's image as the base — target-as-base-image composition. Layer caching is Docker-like ("If an Earthfile command is run again, and the inputs to that command are the same, then the cache layer is reused"), but the *cache entity is the named target*, not the position in some file: a toolchain target builds once and any set importing it reuses its layers ([Earthfile reference](https://github.com/earthly/earthly/blob/main/docs/earthfile/earthfile.md)).

**Caching arsenal** ([caching-in-earthfiles](https://github.com/earthly/earthly/blob/main/docs/caching/caching-in-earthfiles.md)): layer cache (prefix chains within a target); cache mounts (`RUN --mount type=cache`, global via `id`, sharing modes `locked`/`shared`/`private`); `SAVE IMAGE` recommended as a **"manual cache"** at strategic points; auto-skip (cloud-global whole-target skip). Documented gotchas: ARGs must be declared "as late as possible" (`--global` ARGs poison every target's cache), secrets deliberately excluded from cache keys, cache mounts can grow unboundedly and "reusing state from a previous run can be a source of build inconsistency."

**Meets the target?** At component granularity, yes: per-toolchain target = one build per machine, reused by every set. Set images are still sequential chains, so a set's own suffix still rebuilds on composition — the same trade as (a), but with stable component identities.

**Worth stealing:** named, version-pinned targets as the cache identity for toolchains; SAVE IMAGE/tags as manual cache points (our Images-screen component rows); the ARG-late-declaration rule (≈ "versions pinned everywhere, CACHEBUST dies"); cache-mount sharing modes for concurrent builds.

## 4. docker buildx bake + BuildKit cache semantics

**Model.** Bake = declarative multi-target builds: `target` blocks with `inherits` (conflicts: "the target that appears last in the `inherits` list takes precedence"), `contexts` (pin `docker-image://alpine@sha256:…`; or `target:base` to compose from another target's output without touching its Dockerfile), `dockerfile-inline` (a *generated Dockerfile* fed from config — bake's version of strategy (a)), `matrix` (variant forking), `cache-from`/`cache-to` per target ([bake reference](https://docs.docker.com/build/bake/reference/)).

**Cache semantics.** BuildKit layer cache is strictly prefix-chained; best practice is to order layers stable-expensive-first, volatile-last, and keep inputs minimal ([build cache](https://docs.docker.com/build/cache/), [optimization](https://docs.docker.com/build/cache/optimize/)). Cache mounts keep package-manager downloads warm across rebuilds; external cache (registry `type=registry` ref) shares cache across builders/machines.

**Meets the target?** Same as (a) — bake *is* strategy (a) with better orchestration (groups = our "Build all = base + every component"; `no-cache-filter` = per-component forced rebuild; matrix = per-set variants). Nothing here solves strategy (b)'s merge problem; `COPY --from=<external image>` exists as a mechanism ([multi-stage docs](https://docs.docker.com/build/building/multi-stage/): "You can use the `COPY --from` instruction to copy from a separate image…") with last-writer-wins file semantics and no config (ENV/labels) inheritance.

## 5. Official-image layering practice (Docker best practices)

The canonical apt discipline ([best practices](https://docs.docker.com/build/building/best-practices/)): **always `RUN apt-get update && apt-get install -y … && rm -rf /var/lib/apt/lists/*` in one RUN** — separate `apt-get update` layers go stale and serve old packages after cache hits; version pinning (`s3cmd=1.1.*`) is the sanctioned cache-buster; official Debian/Ubuntu images run `apt-get clean` automatically ([debuerreotype](https://github.com/debuerreotype/debuerreotype)); pin base images by digest for reproducible `FROM`s; sort package lists alphanumerically; "create reusable stages — Docker only needs to build the common stage once." Also: `ENV` is itself a layer — you cannot unset it in a later layer.

**Meets the target?** This is the hygiene layer *both* strategies need; it is the recipe-writing standard our toolchain fragments should encode and lint.

## 6. Jib (layer granularity rationale)

"Jib separates your application into multiple layers, splitting dependencies from classes… you only deploy the layers that changed" + "Rebuilding your container image with the same contents always generates the same image" ([Jib README](https://github.com/GoogleContainerTools/jib)). Java-specific, daemonless — cited here as independent confirmation that *splitting by change frequency* and *bit-identical rebuilds* are the two levers of composable-image caching. Its layer split (dependencies / resources / classes, ordered by change frequency) is the same principle as devcontainer's feature-per-layer and Nix's per-store-path layers.

## 7. apko / melange (declarative image composition)

**Model.** OCI images built from a YAML of apk package lists + env + entrypoint, **no RUN equivalent** — "apko files are fully declarative and allows apko to make stronger statements about the contents of images… fully bitwise reproducible and can generate SBOMs covering their complete contents"; "Fast. apko aims to build images in ms." Bespoke tooling must be packaged as apk first (melange); the sanctioned hybrid is "build a base image with apko and melange, then use traditional tooling such as Dockerfiles for the final step" ([apko README](https://github.com/chainguard-dev/apko)).

**Meets the target?** Yes — composition is a *recomputation*, ms-cheap, deterministic; package state (apk DB) is generated fresh per build, so there is nothing to merge.

**Lesson for us:** the only demonstrated way to keep a real package manager in a *merged/composed* image is to make composition regenerate the package DB per compose. If oc-sandbox wanted (b) with apt, the honest analogue is a per-set recomposition step (rpm-ostree model, below), not layer-stacking of prebuilt apt images.

## 8. umoci + buildah (the actual fs-merge tooling)

- **umoci** (OCI reference implementation): `umoci unpack --image … bundle` → edit `bundle/rootfs` → `umoci repack`; plus `umoci insert`. Used in production by KIWI/Open-Build-Service (openSUSE since 2016), Stacker, LXC, Incus ([README](https://github.com/opencontainers/umoci)). This is the OCI-native machinery strategy (b) would use — and it is deliberately "small and unopinionated": **collision and package-state semantics are the compositor's problem.**
- **buildah** (podman's build engine): `buildah from` → `buildah mount` (direct rootfs manipulation, "coreutils interface to build images") → `buildah commit`; Podman uses Buildah's Go code for `podman build` ([README](https://github.com/containers/buildah)). Rootless-capable, scriptable — a native-podman implementation path for merge-style sets, with the same semantic vacuum around dpkg/pip/npm state.

**Meets the target?** Strict sharing: yes — components are tagged images built once; sets are assembled without rebuilding components. The risk the map flagged is real and unhandled by the tools themselves.

## 9. rpm-ostree / OSTree (package-state recomposition)

The hybrid image/package system behind Fedora CoreOS/Silverblue. Key facts ([rpm-ostree](https://coreos.github.io/rpm-ostree/)): layering "constructs a new filesystem root" — never mutates a merged tree in place; "rpm-ostree moves the RPM database to `/usr/share/rpm`, since we want one per root `/usr`" — **exactly one package DB per image root, regenerated per compose**; base commits "are released as coherent wholes, tested together"; client state distinguishes layered packages explicitly to avoid "package drift."

**Meets the target?** Yes, with composition cost per set (a full rpm solve + compose per treefile). It is the strongest evidence that (b)-style sharing *with a real package manager* requires per-compose recomposition of package state.

## Recurring merge-filesystem pitfalls (consolidated)

| State | What breaks on naive merge | How prior art handles it |
| --- | --- | --- |
| dpkg status (`/var/lib/dpkg/status`, apt lists) | Two component images each carry their own; `COPY --from` stacking = last-writer-wins → apt believes wrong package sets; broken upgrades/removals | Sequential single-build (devcontainer, official images); regenerate per compose (apko, rpm-ostree); no package DB at all (Nix) |
| pip metadata (`/usr/local/lib/pythonX/site-packages`) | Two components writing the same site-packages; colliding `*.dist-info` and console scripts | Same-layer install discipline; Nix per-package prefixes; collision-checked unions |
| npm `-g` (`/usr/local/lib/node_modules`, bin symlinks) | Two components installing overlapping global packages/symlinks | Sequential builds (devcontainer runs node feature once per image); Nix store isolation |
| `/usr/local` generally | Silent file overwrite between components | devcontainer namespaces its *own* machinery (`/usr/local/devcontainer-features/<id>`); buildEnv fails on content mismatch (`checkCollisionContents`); umoci/buildah leave it to the compositor |
| ENV composition | `ENV` is a layer; later layers can't unset; merge of two image configs is undefined (only the final stage's config survives `COPY --from`) | Positional ENV emission in canonical order (devcontainer CLI); explicit merge rules (spec: booleans OR'd, lists concatenated); Nix config attrset single-owner; bake `inherits` documented last-wins |

## Naming & canonicalization tricks worth stealing

1. **Deterministic global order via comparator, not list**: devcontainer's Round Stable Sort (fully-qualified ID → version → option count → sorted keys/values → digest) makes identical sets produce identical chains on every machine.
2. **Order via recipe-declared edges**: `dependsOn`/`installsAfter` (+ user override, error on inconsistency) instead of a hand-maintained global sequence.
3. **Content-addressed identity**: feature equality = manifest digest + options; Nix store paths; Earthly named targets. Our set-image identity (content-addressed from the set) has this shape.
4. **Positional stable names**: `consecutiveId = ${id}_${idx}` for internal paths/staging.
5. **Per-machine lockfile with sha256 integrity** + explicit `outdated`/`upgrade` refresh commands (replaces CACHEBUST; matches the map's "refresh is explicit" decision).
6. **Static timestamps / pinned versions everywhere** — non-constant mtime "prevents deduplication" (Nix); version pins are the sanctioned cache-buster (Docker).
7. **Cache mounts keyed by package manager** (apt `sharing=locked`) so the first build of a never-built toolchain doesn't redownload the world.
8. **Tags as manual cache points** (Earthly SAVE IMAGE guidance) — maps directly to Images-screen component rows.
9. **Rename/deprecate discipline**: `legacyIds` + version continuation + fold-into-successor-options for the edition → bundle → set migration.

## Read-across to the two candidate strategies

**Strategy (a) — generated per-set Dockerfile, global canonical order.** Directly validated by devcontainer Features at production scale, on Podman too. Meets the measurable target under two disciplines: (i) one layer per toolchain, recipes pinned and apt-hygienic (§5); (ii) the global order must be *stable and append-friendly* — inserting a toolchain mid-chain rebuilds every downstream toolchain's layer in that workspace's image (podman prefix-chain semantics), so the order wants the Round-Stable-Sort property (set-derived, not user-listed) plus recipe-level `installsAfter` edges. Never-built toolchain = one build, shared thereafter by every workspace whose set prefix reaches it; already-built toolchain = cache hit + seconds of image export. Residual costs: per-workspace final export (cheap); cache-mount hygiene for first-build downloads. No package-state pitfalls at all — everything installs sequentially into one coherent rootfs.

**Strategy (b) — built-once component images, fs-merged.** The record is blunt: **no examined prior art merges prebuilt FHS images' package-manager state; every safe system either regenerates the package DB per compose (rpm-ostree, apko) or eliminates shared mutable state (Nix), and the raw merge tools (umoci, buildah) push the problem to the compositor.** A (b) for oc-sandbox therefore means, per set, a recomposition step that rebuilds dpkg/pip/npm coherence (rpm-ostree model) plus a collision policy (buildEnv model) — doable with umoci/buildah on podman, but it is new mechanism with new failure modes, and it re-adds per-set composition cost anyway. What (b) buys — strict sharing independent of order — Nix gets by construction and Earthly gets halfway via named targets.

**Hybrid worth flagging for the map** (Earthly's shape, in our podman world): per-toolchain *content-addressed component builds* whose results are referenced as stages/contexts (bake `contexts`/`target:base`) into a generated per-set Dockerfile. Components build once per machine (stable identity, version-pinned); sets compose via strategy (a)'s generated Dockerfile; cross-set sharing rides the prefix chain, extended by BuildKit-style stage reuse. This preserves (a)'s sequential-install coherence while giving each toolchain an Earthly-style stable cache identity — and it needs no package-state recomposition.
